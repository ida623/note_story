【畫面的積木】

元件（Component）是 Angular 的基本單位

🎬 晴光故事

林伯帶小晴從一樓走起：「百貨公司不是一整棟，是一櫃一櫃拼起來的。」

每個專櫃＝一個元件，每個專櫃都有四樣東西：

  • 樣板（Template）＝櫃位的招牌和陳列，客人眼睛看到的樣子
  • 類別（Class）＝櫃長腦袋裡的事：今天剩幾件、客人結帳後要做什麼
  • 樣式（Styles）＝這櫃自己的裝潢配色，不會刷到隔壁櫃
  • 中繼資料（Metadata）＝專櫃登記證：櫃號叫什麼（selector）、要用哪些設備（imports）

「大到整層美食街，小到一台試吃推車，都可以是一個專櫃。」

🗺️ 圖解｜一個專櫃（元件）的四個組成

Angular 應用程式由元件組成：大到一整頁、小到一顆按鈕，都能做成獨立元件。每個元件通常包含四個部分：

  • 樣板（Template）：畫面的 HTML 結構。
  • 類別（Class）：用 TypeScript 寫的狀態與行為。
  • 樣式（Styles）：元件自己的 CSS、SCSS 或 Less。
  • 中繼資料（Metadata）：寫在 @Component 裝飾器裡，說明選擇器、匯入項目與檔案位置。
import { Component } from '@angular/core';

@Component({
  selector: 'app-user-profile',
  standalone: true,
  templateUrl: './user-profile.component.html',
  styleUrl: './user-profile.component.css'
})
export class UserProfileComponent {
  userName = '王小明';

  onButtonClick(): void {
    console.log('按鈕被點擊了');
  }
}

建立元件可以用指令 ng generate component user-profile，或簡寫 ng g c user-profile。新版 CLI 產生的元件預設就是 standalone。

Angular 19 起 standalone: true 是預設值，可以不寫出處；這裡寫出來是讓新舊寫法的差異一眼可見。

【新舊架構對照】

standalone 與 NgModule

🎬 晴光故事

林伯翻出一疊舊合約：以前晴光的櫃位全是聯營制（NgModule），每個櫃位要先登記在某個聯營集團名下，由集團統一安排：

  • declarations＝集團旗下的櫃位名單（這團自己的櫃）
  • imports＝向別的集團借收銀機、借保全
  • exports＝本集團開放給別人共用的設備
  • providers＝集團統一配的共用人員（像清潔阿姨）

小晴想改成自營專櫃（standalone）：每櫃自己列設備清單（imports），要什麼寫什麼，不用跟集團報備。開幕時直接開門營業（bootstrapApplication），不用先去集團總部（AppModule）報到。

林伯提醒：「聯營不是錯，只是舊。很多老櫃都還是這套合約，妳要看得懂。」

🗺️ 圖解｜聯營制（NgModule）對照自營專櫃（standalone）

standalone 元件像自己帶行李清單的旅客：需要哪些元件、指令或管道，直接列在自己的 imports，不必先登記到某個 NgModule。

@Component({
  standalone: true,
  imports: [UserCardComponent],
  template: '<app-user-card />'
})
export class HomeComponent {}

NgModule 則像傳統的功能包裹（模組容器），舊專案用它把相關的元件與相依項目集中組織。現代 Angular 官方建議所有新程式改用 standalone 元件；standalone 應用程式由 bootstrapApplication 直接啟動根元件，不需要 AppModule官方建議standalone 啟動。維護既有專案時，下面四個 NgModule 屬性仍要看得懂：

📝 查證更正：原筆記寫「Angular 應用至少需要一個根模組（AppModule）」，查證後更正：那是 NgModule 時代的規則，standalone 應用程式不需要任何 NgModule

屬性 用途
declarations 宣告屬於這個模組的非 standalone 元件、指令與管道；同模組內可以互相使用。
imports 匯入其他模組或 standalone 項目，取得它們提供的功能。
exports 把自己的項目公開，讓匯入這個模組的一方使用。
providers 註冊服務，讓依賴注入系統可以取得。 
@NgModule({
  declarations: [LegacyCardComponent],
  imports: [CommonModule],
  exports: [LegacyCardComponent],
  providers: [UserService]
})
export class SharedModule {}

NgModule 是舊寫法、不是錯誤寫法；既有專案很可能整包都是這個樣子。新專案通常改用 standalone 元件，服務註冊移到應用程式層級的 providers。

【樣板結構】

不留下外殼的 ng-container

🎬 晴光故事

化妝品樓層想把三支口紅綁成一組促銷。小晴原本要去買壓克力展示盒，林伯遞給她一條橡皮筋：「綁起來就好，櫃台上何必多一個盒子佔位子？」

ng-container 就是這條橡皮筋：把多個元素綁成一組，畫面上卻不會多一層盒子（DOM 標籤）來佔位、亂掉排版。

🗺️ 圖解｜用 div 包 vs 用 ng-container 包

ng-container 像透明資料夾（邏輯容器）：能把多個節點包成一組，卻不會在頁面上產生真正的 DOM 元素，所以不會多出一層標籤去干擾版面或樣式。

@for (item of menuList; track item.id) {
  <ng-container>
    <a>{{ item.name }}</a>
    <span>{{ item.description }}</span>
  </ng-container>
}

【先寫好、等著上場】

ng-template 與 ngTemplateOutlet

🎬 晴光故事

服務台抽屜裡收著一顆**「暫停營業」印章**：先刻好，平常收著，不會出現在任何公告上。

哪天哪個櫃位要公休，再拿出來蓋在公告上＝ngTemplateOutlet。印章上留了空格「＿＿櫃暫停營業」，蓋的時候才把櫃名填進去＝context。

🗺️ 圖解｜刻印章、收抽屜、需要時再蓋

ng-template 像先搭好、還沒推上舞台的布景（樣板片段）：Angular 不會直接顯示它，必須由控制流程或 ngTemplateOutlet 把它實例化才會出現。ngTemplateOutlet 的 outlet 意思是「放置的出口」，看到 xxxOutlet 都可以想成「某個東西被放到這裡」，跟路由的 router-outlet 是同一種命名。

<ng-template #emptyState let-message="message">
  <p>{{ message }}</p>
</ng-template>

<ng-container
  *ngTemplateOutlet="emptyState; context: { message: '目前沒有資料' }">
</ng-container>

舊式的 *ngIf、*ngFor 這些結構型指令，會在編譯時展開成樣板；Angular 17 之後有了內建控制流程，新程式優先用 @if、@for 與 @switch（〈指令與資料綁定〉細講）。

@if (isLoggedIn) {
  <p>歡迎回來</p>
} @else {
  <p>請先登入</p>
}

【組合元件】

ng-content 內容投影

🎬 晴光故事

一樓入口有一排廣告燈箱：燈箱（子元件）是百貨統一訂做的，外框和尺寸都固定；裡面放什麼海報，由各專櫃（父元件）決定。

  • 多格燈箱的每一格貼了標籤（select），例如「這格放主打商品」。
  • 有一次專櫃把海報套了一層透明袋（被 ng-container 包住），燈箱認不出它是主打，就被塞進「其他」那格。在袋子上貼一張「我是主打」貼紙（ngProjectAs）就解決了。

🗺️ 圖解｜燈箱留空位，海報由專櫃決定

內容投影（Content Projection）像子元件預留插槽、由呼叫端決定塞什麼進去：子元件定版型，父元件供內容。

<!-- panel.component.html -->
<header><ng-content select="[panel-title]" /></header>
<main><ng-content /></main>

<!-- 使用元件 -->
<app-panel>
  <h2 panel-title>課程公告</h2>
  <p>今天開始學 Angular。</p>
</app-panel>

要投影的節點如果被額外的容器（例如 ng-container）包住，select 選擇器會配對不到，內容就掉進沒有選擇器的預設插槽。這時可以在該節點加 ngProjectAs，明確告訴 Angular 要把它當成哪種選擇器來配對。

  • Component：元件，負責一塊畫面與它的互動。
  • Template：樣板，描述元件的畫面結構。
  • Content Projection：內容投影，把父層準備的內容放進子元件的插槽。
  • NgModule：傳統的模組容器；standalone 架構下不再需要。

隨堂測驗

Q1. 現代 Angular 中，元件標示 standalone: true 的意義是什麼？

  • (A) 元件自己管理 imports，不必宣告在任何 NgModule 的 declarations 裡
  • (B) 元件不能再匯入其他元件或管道
  • (C) 元件只能使用行內樣板，不能用 templateUrl
  • (D) 元件會自動註冊成全域服務
看答案

答案：(A) standalone 元件把需要的東西列在自己的 imports，脫離 NgModule 的登記制。

Q2. 元件的 TypeScript 類別負責什麼？

  • (A) 這塊畫面的狀態與事件處理邏輯
  • (B) 定義畫面的 HTML 結構
  • (C) 限制樣式只作用在這個元件
  • (D) 決定路由配對到哪個頁面
看答案

答案：(A) HTML 結構是樣板的事、樣式隔離是樣式與封裝的事；類別管狀態與行為。

Q3. ng-container 最重要的特性是什麼？

  • (A) 能把多個節點包成一組，但不會產生額外的 DOM 元素
  • (B) 會自動套用元件的樣式封裝
  • (C) 只能搭配 ngTemplateOutlet 使用
  • (D) 它的內容預設不會顯示，要另外實例化
看答案

答案：(A) 它是邏輯容器；「內容預設不顯示、要實例化」說的是 ng-template。

Q4. 為何 ng-template 的內容預設不會顯示？

  • (A) 它定義的是樣板片段，要由控制流程或 ngTemplateOutlet 實例化才會出現
  • (B) 它必須先在 NgModule 的 declarations 宣告
  • (C) 它只有在元件銷毀前的最後一次變更偵測才渲染
  • (D) 它的內容會被 ng-content 的插槽攔截
看答案

答案：(A) ng-template 是先寫好、等著被放上舞台的布景，不實例化就不出現。

Q5. ngTemplateOutlet 的用途是什麼？

  • (A) 在指定位置實例化某個 ng-template，還能用 context 帶參數
  • (B) 把子元件的樣板整份複製到父元件
  • (C) 宣告一個新的路由出口
  • (D) 把元件的樣式穿透到子元件
看答案

答案：(A) outlet 是「放置的出口」：把參照到的樣板放進目前位置，context 可傳值。

Q6. 內容投影（ng-content）最適合解決哪種需求？

  • (A) 子元件定共同版型，內容由父元件決定
  • (B) 父元件要讀取子元件的私有屬性
  • (C) 兩個兄弟元件要共用同一份服務
  • (D) 清單重新排序時要重用 DOM 節點
看答案

答案：(A) ng-content 是元件預留的插槽；共用服務靠依賴注入、清單重用靠 track。

Q7. 傳統 NgModule 的 declarations 放什麼？

  • (A) 屬於該模組的非 standalone 元件、指令與管道
  • (B) 要提供給依賴注入的服務
  • (C) 要公開給其他模組使用的項目
  • (D) 應用程式啟動時要先執行的初始化函式
看答案

答案：(A) 服務放 providers、公開項目放 exports；declarations 是模組自有的宣告項目。

Q8. 投影的節點被 ng-container 包住、select 配對不到時，該怎麼辦？

【Angular 17+ 控制流程】

@for 與 track

🎬 晴光故事

週年慶前晴光要大搬風，好幾個專櫃換位置。美玲姐手上有兩種名冊：

  • 用統一編號（track item.id）認櫃：搬完家，她知道「阿美鞋店還是阿美鞋店」，只要把招牌搬過去就好。
  • 用櫃位號碼（$index）認櫃：一搬家，她以為 B12 還是原來那家，結果認錯一堆，只好全館重新登記（整批重建 DOM）。

所以只有「永遠不會換位子」的櫃位（靜態清單），才適合用櫃位號碼點名。

🗺️ 圖解｜用統一編號認櫃 vs 用櫃位號碼認櫃

@for (course of courses; track course.id;
      let i = $index, first = $first, count = $count) {
  <article [class.first-item]="first">
    {{ i + 1 }} / {{ count }}：{{ course.name }}
  </article>
} @empty {
  <p>目前沒有課程</p>
}

track 像每件行李上的固定識別牌：清單重新排序或更新時，Angular 靠它認出哪個 DOM 節點仍代表同一筆資料，只更新有變的項目，不必整批拆掉重建。沒有穩定識別值時，資料一變就重建所有 DOM，清單一大就慢。

資料有穩定 ID 就用 item.id；只有「不會插入、刪除、重新排序」的靜態清單，才適合用 $index 追蹤。$index、$first、$count 這些開頭的 $ 表示是 Angular 提供的內建變數，跟你自己資料裡的變數區隔開來。

🗺️ 圖解｜舊地名（星號指令）對照新地名（控制流程）

既有專案仍到處是星號語法。結構型指令會新增、移除 DOM 元素：*ngIf、*ngFor、*ngSwitchCase、*ngSwitchDefault 都要加星號；容器上的 [ngSwitch] 本身不加。

  <p *ngSwitchDefault>準備中</p>

新程式優先用 @if、@for、@switch；星號寫法是維護舊專案時要認得的字彙。

  • 事件綁定 ( )＝服務鈴：客人在現場按了，就通知後台「有人需要幫忙」
  • 雙向綁定 [( )]＝服務台的共用白板：你寫上去我看得到，我擦掉改寫你也看得到——其實就是「遙控器＋服務鈴」一起用

🗺️ 圖解｜四種綁定的資料方向

語法 方向 用途
{{ title }} 類別 → 畫面 文字插值。

方括號綁資料、圓括號接事件；雙向綁定＝屬性綁定＋事件綁定

【設計觀念】

單向資料流與 MVVM

🎬 晴光故事

林伯指著頂樓的水塔：「水從水塔（類別）往下流到每層樓的水龍頭（畫面）。樓下的人想改水量，要打電話通知頂樓（事件），由頂樓調整。哪層的水髒了，就一路往上查，一定找得到源頭。」這就是單向資料流。

他又指著美食街：

  • Model＝廚房的食材和食譜（資料與規則）
  • View＝客人看到的餐桌（畫面）
  • ViewModel＝服務生：把廚房的菜端上桌，也把客人的點餐傳回廚房。Angular 的元件類別就像這位服務生

🗺️ 圖解｜水塔往下流：單向資料流與 MVVM

Angular 的常態是：元件類別的狀態推動畫面更新（類別 → 畫面），畫面上的操作透過事件通知類別改狀態（畫面 → 類別）。只綁資料不綁事件時，在畫面上怎麼點，類別裡的值都不會變——這就是單向資料流；方向清楚，出問題時才追得到源頭。

MVVM 是一種理解方式（Model–View–ViewModel，資料層、畫面層、居中銜接層）：

  • Model：應用程式的資料與規則。
  • View：使用者看到的樣板。
  • ViewModel：把狀態與操作提供給 View；在 Angular 裡，元件類別扮演相近的角色。

MVVM 是幫助理解的地圖，不必把 Angular 每個機制硬套進去。

【元件的一生】

生命週期 hook：在對的時機做對的事

🎬 晴光故事

林伯拿阿哲的到職流程當例子：

  • constructor＝錄取報到：領識別證和工具（依賴注入在這裡發生），但還沒開始做事
  • ngOnChanges＝主管交辦的內容改了，要跟著調整
  • ngOnInit＝第一天正式上工：整理桌面、做開工準備（只做一次）
  • ngAfterViewInit＝團隊成員都到齊了，終於可以找同事開會
  • ngOnDestroy＝離職前交接：退掉訂的報紙、關掉鬧鐘、歸還門禁卡

「變更偵測」就像樓管定時巡櫃，看看大家的狀態有沒有更新。

🗺️ 圖解｜一位專櫃人員（元件）的一生

Angular 建立元件後會反覆進行變更偵測（檢查綁定的資料有沒有變、需不需要更新畫面），直到元件被移除、銷毀。生命週期 hook（掛勾函式，Angular 在特定時機自動呼叫的方法）讓你把程式掛在這些時機上。常用的四個：

Hook 適合用途
ngOnChanges 回應輸入值的變化；元件有綁定的輸入值時才會被呼叫。
ngOnInit 輸入初值都就緒後，執行一次初始化。
ngAfterViewInit 檢視與子元件都建立完成後，使用檢視查詢的結果。
ngOnDestroy 元件退場前，取消訂閱、清計時器、釋放資源。

完整的初始化順序是 constructor → ngOnChanges → ngOnInit → ngDoCheck → ngAfterContentInit → ngAfterContentChecked → ngAfterViewInit → ngAfterViewChecked，銷毀時才是 ngOnDestroy出處；而且 ngOnChanges 只有在元件有綁定的輸入值、且至少一個值變了才會執行出處。

constructor 是 TypeScript 類別本身的建構函式，不算 Angular 的生命週期 hook；依賴注入在這裡發生，但初始化邏輯建議放 ngOnInit。

【父傳子】

Input 是子元件的資料入口

🎬 晴光故事

阿哲被派到美食街的現做鬆餅櫃。他不自己決定做什麼口味，而是看外場（父元件）遞來的點餐單做；同一個阿哲，可以替不同客人做不同口味（元件重用）。

[course]="selectedCourse" 就是「把這張點餐單（父元件的 selectedCourse）交到阿哲的 course 欄位」。

🗺️ 圖解｜點餐單由外場（父）交給廚師（子）

子元件能被多個父元件重用（例如課程卡片），資料就不能寫死在子元件裡，而是由父元件傳進來。

// 子元件
@Input({ required: true }) course!: Course;

<!-- 父元件樣板 -->
<app-course-card [course]="selectedCourse" />

方括號左側的 course 是子元件公開的輸入名稱，右側的 selectedCourse 是父元件的運算式——「子元件的變數＝父元件的變數」。新版 Angular 另有以 signal 為基礎的 input() 寫法；讀舊程式時看到的多半是 @Input。

【子傳父】

Output 把事件送回父元件

🎬 晴光故事

鬆餅做好，阿哲按一下出餐鈴（emit），外場聽到鈴聲（(selected)）就來端；$event 就是那盤鬆餅。

林伯補充：鈴聲的名字要描述「發生了什麼」（「餐好了」selected），不要取成命令別人（「快來端」）。

🗺️ 圖解｜出餐鈴：子元件把事件送回父元件

// 子元件
@Output() selected = new EventEmitter<Course>();

choose(): void {
  this.selected.emit(this.course);
}

<app-course-card
  [course]="course"
  (selected)="openCourse($event)" />

父元件用圓括號接子元件的輸出事件，$event 就是 emit 送出來的資料。事件名稱描述「發生了什麼」（selected、deleted），不要取成命令句。

新版 Angular 也提供 output() 寫法；EventEmitter 仍是最常見、必須看懂的形式。

【呼叫子元件】

樣板參照變數與 ViewChild

🎬 晴光故事

  • 樣板參照變數 #counter＝在遙控器上貼名字標籤，要用時直接拿起來按
  • @ViewChild＝樓管查員工名冊找到阿哲，再請他做事
  • static: false（預設）：新人要等報到流程全跑完（ngAfterViewInit）才會出現在名冊上；樓管在 ngOnInit 就去查，名冊上還找不到人（undefined）

林伯提醒：「能用點餐單（Input）和出餐鈴（Output）溝通，就別直接跑進廚房指揮阿哲，彼此比較不會綁死。」

🗺️ 圖解｜查員工名冊：ViewChild 什麼時候拿得到

只在樣板裡呼叫子元件的公開方法時，樣板參照變數（# 開頭，替樣板中的元素取名）最簡單：

<app-counter #counter />
<button (click)="counter.increment()">加一</button>

父元件的 TypeScript 要拿到子元件實例時，用檢視查詢 @ViewChild：

@ViewChild(CounterComponent)
counter?: CounterComponent;

ngAfterViewInit(): void {
  this.counter?.increment();
}

查詢結果何時可用取決於 static 設定：預設（static: false）在 ngAfterViewInit 之前解析，所以 ngOnInit 拿到的是 undefined；設 static: true 則在 ngOnInit 之前就解析好，但結果不會隨檢視變動更新出處。

能用 Input／Output 描述父子關係時，通常比直接呼叫子元件方法更鬆耦合。

【顯示轉換】

Pipe 專心把值轉成適合顯示的樣子

🎬 晴光故事

美玲姐的櫃台有一台標價機：商品本身不變，只是印出來的標籤換個樣子（日期換格式、數字加上 $）。

她交代阿哲：「標價機只負責印得好看，不能拿它去下訂單或改庫存。」——也就是不要有副作用、不要發 HTTP 請求。

🗺️ 圖解｜標價機：值流過去，換個樣子顯示

<p>{{ today | date:'yyyy-MM-dd' }}</p>
<p>{{ price | currency:'TWD':'symbol':'1.0-0' }}</p>

管道（Pipe）像水管末端的濾嘴：值流過去、以另一種樣子呈現，來源資料不動。standalone 元件可直接匯入需要的管道（DatePipe、CurrencyPipe…），或匯入包含常用管道的 CommonModule。自訂管道適合可重複、無副作用的顯示轉換，不適合發 HTTP 請求或改資料。

@Pipe({ name: 'initials', standalone: true })
export class InitialsPipe implements PipeTransform {
  transform(name: string): string {
    return name.split(/\s+/).map(part => part[0]).join('');
  }
}

【共用能力】

Service 與依賴注入

🎬 晴光故事

美玲姐的服務台就是晴光的 Service。各櫃需要什麼——發票、提袋、會員查詢——打內線（inject(CourseService)）就送來，不用自己跑出去買（自己 new）。

  • providedIn: 'root'＝全館共用同一個服務台
  • 注入情境（injection context）＝新櫃位只有在進駐登記時能填需求單；營業到一半才跑去補填，服務台不受理（會報錯）

🗺️ 圖解｜全館共用一個服務台

跨多個元件的共用邏輯、資料存取或狀態，抽成服務（Service）。服務經由依賴注入（Dependency Injection，需要什麼由框架送進來，不用自己 new）提供給元件，比元件之間層層呼叫更容易測試與替換。

@Injectable({ providedIn: 'root' })
export class CourseService {
  getCourses(): Course[] {
    return [];
  }
}

元件要拿到服務，用 inject() 函式在類別欄位宣告時直接取：寫 inject(CourseService)，Angular 就把對應的實例送進來，之後用 this.courseService 呼叫它的方法即可。之後的程式裡出現的 this.router、this.heroService、this.http 都是這樣拿到的出處。

import { Component, inject } from '@angular/core';

@Component({ selector: 'app-course-list', /* ... */ })
export class CourseListComponent {
  private courseService = inject(CourseService);
  courses: Course[] = [];

  ngOnInit(): void {
    this.courses = this.courseService.getCourses();
  }
}

inject() 要在元件、指令或服務「建構期間」呼叫——寫在欄位初始值或建構函式本體裡都可以，官方把這種可以呼叫的地方稱為注入情境（injection context）；在其他時機（例如按鈕事件的處理函式裡）呼叫會報錯。

【新寫法概覽】

訊號（signals）：官方現行主推的寫法

🎬 晴光故事

阿哲把晴光的業績板換成一張 Excel 試算表：

  • signal()＝一個儲存格，值改了會自動通知用到它的地方
  • computed()＝公式格（像 =A1*2），只有 A1 變了才重算
  • effect()＝設定「A1 一變就寄 email 給林伯」這種附帶動作
  • input()＝鎖定的儲存格，專櫃只能看、不能改

以前的寫法（裝飾器）則像樓管每隔一陣子把整張表從頭掃一遍，看看哪裡變了。

🗺️ 圖解｜業績試算表：signal、computed、effect

上面講的 @Input／@Output／EventEmitter 是裝飾器寫法，既有專案裡大多長這樣。現行的主要寫法是訊號（signal，一個「會通知誰在用我」的值）：元件輸入以 input() 為主，@Input 裝飾器仍完整支援出處。新專案會直接遇到訊號，兩種寫法對照如下。

要做的事 裝飾器寫法 訊號寫法（官方現行）
接收父元件的值 @Input() value = 0; value = input(0);（讀值要加括號：this.value()）
必填的輸入 @Input({ required: true }) id!: string; id = input.required<string>();
往父元件送事件 @Output() saved = new EventEmitter<void>(); saved = output<void>();
自己管一個會變的值 普通屬性，靠變更偵測掃描 count = signal(0);，改值用 this.count.set(1) 或 update()
由其他值算出來的值 getter 或在樣板裡算 double = computed(() => this.count() * 2);——來源變了才重算

signal() 建立一個可讀可寫、會通知使用者的值；computed() 從其他訊號算出唯讀的值，來源沒變就不重算；effect() 在訊號變動時做副作用（例如寫入瀏覽器儲存）。input() 回傳的是唯讀訊號，所以只能讀、不能在子元件裡改。

舊專案看得懂裝飾器，新專案直接寫訊號

靜態資產放哪裡

🎬 晴光故事

晴光有兩間倉庫：新大樓（Angular 18+）的倉庫叫 public/，老大樓的叫 src/assets。圖片、字型都收在這。

【樣式架構】

全域樣式與元件樣式各司其職

🎬 晴光故事

小晴寫好了晴光的品牌手冊：

  • 全域樣式＝晴光的品牌手冊：標準色、字體、間距，全館一起遵守
  • 元件樣式＝各櫃自己的佈置，只管自己的櫃位
  • CSS 變數＝替油漆桶取名字（「晴光橘」）：換掉這桶油漆，全館用到它的地方一起變色，夜間模式就是這樣切的
  • 第三方套件的基礎樣式像 IKEA 家具附的五金零件：少了它，家具功能都在，但組起來歪七扭八

🗺️ 圖解｜換掉一桶油漆，全館一起變色

全域樣式（styles.css 或 styles.less）放色彩變數、文字規格、間距與重設規則；元件樣式只描述該元件自己。預處理器（SCSS 或 Less，先寫變數與巢狀再編譯成 CSS 的工具）在建立專案時選定最省事，之後也能改檔名並同步修改 angular.json 的 styles 設定。

:root {
  --color-bg: #ffffff;
  --color-text: #202124;
}

:root[data-theme='dark'] {
  --color-bg: #171717;
  --color-text: #f3f3f3;
}

body {
  background: var(--color-bg);
  color: var(--color-text);
}

用第三方 UI 套件（如 Ant Design）時，還要照套件文件載入它的基礎樣式；把基礎樣式拿掉，元件功能還在、外觀卻會整個失靈。

【樣式封裝】

為何父元件的 CSS 套不到子元件

🎬 晴光故事

晴光每個專櫃的油漆都貼著自己的櫃號：你在 A 櫃刷紅漆，不會刷到隔壁 B 櫃（樣式封裝）。

  • :host＝這個櫃位的櫃框本身
  • ::ng-deep＝萬能鑰匙，可以闖進所有櫃位亂刷油漆，林伯（Angular 官方）強烈不建議

想改外包廠商櫃位的外觀，先問廠商有沒有「可調整的選項」（主題 API、CSS 變數），真的沒有才自己動手。

🗺️ 圖解｜每櫃的油漆都貼著自己的櫃號

Angular 預設做檢視封裝（View Encapsulation）：編譯時替每個元件的元素加上專屬的屬性選擇器，像替每間房間的油漆貼上房號，元件樣式就不會外洩污染別的區域。這也是為什麼在父元件寫 p { color: red }，子元件的 <p> 不會變紅。

:host 用來選取元件自己的宿主元素（元件標籤本身，例如 <app-card>）：

:host {
  display: block;
}

:host .title {
  font-weight: 700;
}

::ng-deep 會拆掉封裝、讓選擇器穿透到子元件，今天仍然能用，但 Angular 官方強烈不建議新程式使用，保留它只是為了回溯相容出處。

要客製第三方元件的外觀，優先順序是：套件提供的主題 API、CSS 變數、可設定的 class，再來才是範圍收窄的全域樣式。

【偏好保存】

localStorage、sessionStorage、Cookie 與 Session

🎬 晴光故事

小晴發現，網站的伺服器就像一位健忘的店員：客人每次走進來，他都不記得對方是誰（HTTP 無狀態；但這跟電話有沒有掛斷是兩回事）。所以要靠別的方式「記住」：

  • localStorage＝貼在自家冰箱上的便條：一直都在，家裡每個人（同源的分頁）都看得到
  • sessionStorage＝試衣間的號碼牌：離開試衣間（關閉分頁）就收回
  • Cookie＝晴光會員卡：每次結帳都自動出示給櫃台看
  • 伺服器 Session＝寄物櫃：東西放在晴光，客人手上只拿一張號碼牌

阿哲提醒：把登入權杖（JWT）放 localStorage，就像把家門鑰匙貼在冰箱上——小偷（XSS 攻擊）一進屋就能拿走。

🗺️ 圖解｜要記住的東西放哪裡

📝 查證更正：原筆記寫「HTTP 為無狀態協議，每次請求、獲取數據，前端頁面與服務端都需要重新連接」，查證後更正：無狀態指的是伺服器不保留前一個請求的狀態，與底層連線是否重用是兩回事——HTTP/1.1 起預設 keep-alive，同一條 TCP 連線可以連續送很多個請求

機制 生命週期與範圍 適合用途
localStorage 同源下持續保存，同源的各分頁都讀得到 主題、語言等非敏感偏好
sessionStorage 只限單一分頁的工作階段，關閉即消失 單次流程的暫存狀態
Cookie 可設過期時間，符合規則時隨每次 HTTP 請求送出 由伺服器讀取的識別資訊（單顆約 4KB）
伺服器 Session 資料放伺服器，瀏覽器通常只拿一個識別碼 登入狀態與敏感的工作階段資料

Web Storage（localStorage 與 sessionStorage 的統稱）只能存字串，物件要先用 JSON 轉換。敏感憑證（例如登入用的 JWT，JSON Web Token，一串夾帶登入身分、附簽章的權杖字串）不要只因為方便就放 localStorage出處。

📝 查證更正：原筆記把「用戶登入狀態（配合 JWT token）」列為 localStorage 的適用場景，查證後更正：localStorage 的內容任何同源的 JavaScript 都讀得到，跨站腳本攻擊（XSS）一旦得手就能整包帶走；OWASP 建議權杖不要放在 Web Storage

【主題初始化】

在第一個畫面出現前套回偏好

🎬 晴光故事

晴光每天早上開門前先把燈光調好：如果開門後才調，客人會先看到亮白燈，再突然變暗（畫面閃一下）。

provideAppInitializer 就是開門前的檢查清單：清單上的事做完（Promise / Observable 完成），才拉開鐵門讓客人進來（建立根元件）。

🗺️ 圖解｜開門前先調好燈光

主題存進 localStorage 之後還差一步：重新整理頁面時，要在畫面出現前把它讀回來套用，不然會先閃一下預設主題。Angular 的應用程式初始化機制就是做這件事。要注意寫法換過一輪：APP_INITIALIZER 這個舊寫法自 Angular 19 起標記為棄用，官方建議改用 provideAppInitializer（出處）：

import { provideAppInitializer, inject } from '@angular/core';

export const appConfig = {
  providers: [
    provideAppInitializer(() => {
      const theme = inject(ThemeService);
      theme.apply(localStorage.getItem('theme') ?? 'light');
    })
  ]
};

啟動流程概念上是：執行進入點 main.ts → 讀取應用程式設定 app.config.ts → 執行所有初始化函式 → 建立根元件。初始化函式回傳 Promise（代表一件還沒完成的非同步工作）或 Observable（RxJS 的資料流物件，值會陸續送來、要訂閱才拿得到）時，Angular 會等它完成才往下走。

【瀏覽器安全邊界】

同源政策與 CORS

🎬 晴光故事

晴光樓上是住宅大樓，保全大哥這樣解釋：

  • 同源＝同一個地址、同一個大門、同一間房號（協定＝走哪個大門、主機＝地址、埠號＝房號），三樣都一樣才算自家人
  • CORS 像住戶在警衛室留訪客名單：是被拜訪的住戶（伺服器）說「這個人可以上來」，不是訪客（前端）自己說了算

🗺️ 圖解｜訪客名單由住戶（伺服器）決定

兩個網址要通訊協定、主機、埠號三者都相同才算同源（路徑不同沒關係）。localStorage 與 sessionStorage 都受同源邊界限制：別的網站讀不到你網站存的東西。CORS（跨來源資源共享）不是把同源政策關掉，而是伺服器透過回應標頭，明確允許特定來源讀取跨來源的回應。

同源＝通訊協定相同＋主機相同＋埠號相同

【網路互動基礎】

Ajax 不是某一套函式庫

🎬 晴光故事

線上晴光的第一個功能是外送：客人用手機點餐，下單後照樣追劇，餐到了再開門拿，不用親自來店裡排隊。

而且是只換掉桌上那盤菜（局部更新），不是把整桌收掉重擺（整頁重載）。

🗺️ 圖解｜點外送：送出請求後不用傻等

Ajax（Asynchronous JavaScript and XML）是一組「在瀏覽器裡非同步交換資料、局部更新畫面」的做法，不是單一技術。名稱裡的 XML 是歷史痕跡，現代更常交換 JSON；實作可以用瀏覽器原生的 Fetch API、Angular 的 HttpClient，或其他 HTTP 工具。

同步請求像站在櫃台前傻等，等到回覆前什麼都不能做；非同步請求像先抽號碼牌，等待期間照常做別的事，結果送到再更新畫面。

非同步不保證回應更快，它讓應用程式不必在等待期間卡住其他工作

【單頁應用程式】

SPA 只換內容、不重載整頁

🎬 晴光故事

林伯想起晴光以前辦過的舞台劇：觀眾一直坐在同一間劇場（同一頁），只是舞台上的布景換了，不用全部人離場再進另一間劇場。

但後台還是要一直送道具上來（API 資料、圖片）；想要「停電也能演」（離線使用），得另外準備發電機（Service Worker）。

🗺️ 圖解｜傳統多頁網站 vs 單頁應用程式

單頁應用程式（Single-Page Application，SPA）先載入一個應用程式外殼（版面骨架），之後的頁面切換由 JavaScript 依操作更新內容，不再整頁重新載入。Gmail 是經典例子：讀信、回信都在同一頁完成。

SPA 帶來流暢切換與前後端分工，但別誤會成「之後都不需要伺服器」：API 資料、按路由切割的程式碼檔、圖片仍會經由網路載入。初次載入速度、搜尋引擎收錄與錯誤處理也要另外設計。「離線也能用」常被當成 SPA 的天生優勢——其實那要另外實作 Service Worker（瀏覽器背景腳本，可攔截請求做快取）之類的機制才有，不是 SPA 內建。

【現代 Angular Router】

設定路由與出口

🎬 晴光故事

小晴在官網做了一張樓層導覽：客人說要去哪（網址），導覽員查表，把對應的專櫃（元件）帶到電梯門口（router-outlet）。

導覽表由上往下查、先查到先算。萬用路由 ** 是「找不到的請洽服務台」，一定要寫在最後一行；寫在第一行的話，所有客人都會被直接帶去服務台。

🗺️ 圖解｜樓層導覽：由上往下，先查到先算

SPA 的網址管理靠路由（Router）：它比對目前網址，把對應的元件放進樣板裡的 router-outlet。

import { Routes } from '@angular/router';

export const routes: Routes = [
  { path: '', redirectTo: 'home', pathMatch: 'full' },
  { path: 'home', loadComponent: () =>
      import('./home.component').then(m => m.HomeComponent) },
  { path: 'users/:id', loadComponent: () =>
      import('./user.component').then(m => m.UserComponent) },
  { path: '**', loadComponent: () =>
      import('./not-found.component').then(m => m.NotFoundComponent) }
];

bootstrapApplication(AppComponent, {
  providers: [provideRouter(routes)]
});

【導覽】

routerLink 與程式式導覽

🎬 晴光故事

  • routerLink="/home"＝電梯旁的固定指示牌
  • [routerLink]="['/users', id]"＝填空式地址：「＿＿樓＿＿櫃」
  • router.navigate()＝接駁車司機：等事情辦完，再依情況載客人過去
  • router.navigateByUrl()＝直接給司機一個完整地址
  • routerLinkActive＝電梯到樓時亮起的燈；exact: true 是「真的到這層才亮」，而不是只要在這台電梯上就一直亮

  [routerLink]="['/users', user.id]"
  routerLinkActive="active">
  {{ user.name }}
</a>

一句話分工：routerLink 決定要去哪裡，routerLinkActive 決定「到了」之後套什麼 CSS class，routerLinkActiveOptions 決定什麼條件算「到了」。首頁 / 這種短路徑預設用部分比對、很容易永遠是「到了」，可設 [routerLinkActiveOptions]="{ exact: true }"（方括號不能省，否則傳進去的是字串）出處 改成精確比對；新版 Router 還接受更細的 IsActiveMatchOptions（可分別指定路徑、查詢參數、fragment——網址 # 後面那一段——的比對方式）。

📝 查證更正：原筆記寫 routerLinkActiveOptions="{exact: true}"（不加方括號），查證後更正：那樣傳進去的是字串不是物件，設定不會生效，必須用屬性綁定的方括號寫法

【路由資料】

路徑參數、查詢參數與巢狀路由

🎬 晴光故事

  • 路徑參數＝櫃位號碼：要去哪一櫃（/users/42）
  • 查詢參數＝到了之後的要求：「我要看新品、價格由低到高」（?tab=history）
  • snapshot＝拍一張照片，之後不會更新；訂閱 paramMap＝監視器直播。同一種櫃換了櫃號（元件被重用，從 42 號到 43 號），只看照片就會一直停在舊櫃號
  • 巢狀路由＝櫃中櫃：大櫃位裡面再分小櫃

🗺️ 圖解｜拆開一個網址：櫃位號碼與要求

// /users/42?tab=history
this.router.navigate(['/users', userId], {
  queryParams: { tab: 'history' }
});

// 只讀一次
const id = this.route.snapshot.paramMap.get('id');

// 跟著變化
this.route.paramMap.subscribe(params => {
  const currentId = params.get('id');
});

路徑參數識別「哪一筆資源」（例如使用者 ID），查詢參數描述「怎麼看」（篩選、排序、分頁）。同一個元件會在參數改變時被重用（例如從 /users/42 切到 /users/43），這時訂閱 paramMap 才收得到新值，只讀一次 snapshot 會停在舊的。

巢狀路由讓子頁面顯示在父路由元件裡的另一個 router-outlet，適合「課程／章節」「設定／分頁」這種層級結構。

【載入順序】

從 index.html 到路由元件

🎬 晴光故事

林伯帶小晴走一遍客人進館的路：大門（index.html）→ 店長迎接（根元件）→ 樓層格局（版面元件）→ 導覽員看客人要去哪（Router 比對網址）→ 帶到櫃位（放進 router-outlet）。

阿哲補充：現代 HTTP 的 keep-alive，像電話不掛斷、連續訂好幾樣東西，而不是每訂一樣就掛掉重撥。

🗺️ 圖解｜客人進館的路線

index.html → 啟動根元件 → 版面元件 → Router 比對網址 → 頁面元件放進 router-outlet

再往下一層，瀏覽器拿到網址後還要做 DNS 查詢、建立連線、送出 HTTP 請求、解析 HTML 與 JavaScript——完整流程見網頁與網路基礎模組的〈從輸入網址到看到網頁〉。「每次請求都做 TCP 三向交握、回應後四次揮手關閉」是早期教學的簡化：HTTP/1.1 起連線預設保持並重用（keep-alive），HTTP/2 在同一條連線上多工，HTTP/3 走 QUIC（建在 UDP 上、把建立連線與加密交握合併的傳輸協定），連線建立和加密合在同一套交握出處。

📝 查證更正：原筆記寫「2. 建立 TCP 連線(三次握手)…5. 關閉 TCP 連線(四次握手)」，查證後更正：HTTP/1.1 起連線預設保持重用，不會每次請求後都關閉；HTTP/3 甚至沒有獨立的 TCP 交握

Q1. Ajax 的核心價值是什麼？

  • (A) 非同步取得資料並局部更新畫面，不必整頁重載
  • (B) 保證每次請求的回應時間更短
  • (C) 把資料格式統一成 XML
  • (D) 讓瀏覽器不再需要發 HTTP 請求
看答案

答案：(A) Ajax 是一組非同步互動做法；它不加速單次回應，資料格式也早就以 JSON 為主。

Q2. 「非同步請求」代表什麼？

  • (A) 送出請求後不必等待，期間可繼續處理其他事
  • (B) 伺服器會用比較高的優先權處理
  • (C) 請求失敗時會自動重試
  • (D) 回應一定比同步請求快
看答案

答案：(A) 非同步解決的是「等待期間卡住」，不是速度，也不含自動重試。

Q3. Angular SPA 中 router-outlet 的角色是什麼？

  • (A) 放置目前網址配對到的路由元件
  • (B) 攔截 HTTP 請求並快取回應
  • (C) 宣告全域樣式的作用範圍
  • (D) 保存路由歷史供上一頁使用
看答案

答案：(A) Router 比對網址後，把對應元件渲染在 outlet 的位置。

Q4. 為何 path: '**' 要放在路由陣列最後？

  • (A) 路由先到先得，放前面會攔截所有網址、永遠顯示 404
  • (B) 陣列最後一筆的優先權最高
  • (C) Angular 規定萬用路由必須是預設路由
  • (D) 放前面會讓延遲載入失效
看答案

答案：(A) 配對由上而下，萬用路由什麼都配得上，放前面就沒有別的路由出場機會。

Q5. 網址 /users/42?tab=history 中，42 與 tab 各屬於哪類？

  • (A) 42 是路徑參數、tab 是查詢參數
  • (B) 42 是查詢參數、tab 是路徑參數
  • (C) 兩者都是路徑參數
  • (D) 兩者都是 fragment
看答案

答案：(A) 路徑參數識別資源（哪個使用者），查詢參數描述檢視方式（看哪個頁籤）。

Q6. 同一個元件會在路由參數改變時被重用，該怎麼拿到新參數？

  • (A) 訂閱 route.paramMap 這類 Observable
  • (B) 只在建構時讀一次 snapshot 就夠
  • (C) 改用 window.location 手動解析網址
  • (D) 在 ngOnDestroy 裡讀取參數
看答案

答案：(A) 元件不重建時 snapshot 停在舊值；訂閱才收得到後續變化。

Q7. routerLinkActive 的用途是什麼？

  • (A) 目前路由配對時，替連結加上指定的 CSS class
  • (B) 點擊連結時觸發程式式導覽
  • (C) 定義連結要前往的路徑
  • (D) 控制路由的配對是精確還是部分
看答案

答案：(A) 去哪裡是 routerLink、什麼算到了是 routerLinkActiveOptions；routerLinkActive 管到了之後的樣式。

Q8. 首頁連結 routerLink="/" 常設 { exact: true }，為什麼？

  • (A) 預設部分比對會讓 / 配到所有路徑，首頁永遠顯示為作用中
  • (B) 不設 exact 首頁路由就無法載入
  • (C) exact: true 會加快路由比對速度
  • (D) 這是啟用巢狀路由的必要條件
看答案

答案：(A) 每個網址都以 / 開頭，部分比對下首頁連結永遠「到了」；exact 改成精確比對。

Q9. 關於現代 HTTP 連線，哪個敘述正確？

  • (A) HTTP/1.1 起連線預設保持重用，不會每次請求後就關閉

【Step 5，建立服務】

資料取得移出元件

🎬 晴光故事

英雄資料交給美玲姐的服務台（Service）。Observable 像訂館訊：訂了（subscribe）館訊才會送來。

of(HEROES) 像先拿影印的舊館訊練習；之後改成真正的出版部（後端 API），讀館訊的人（元件）完全不用改習慣。

🗺️ 圖解｜Step 5：元件只管訂館訊

@Injectable({ providedIn: 'root' })
export class HeroService {
  getHeroes(): Observable<Hero[]> {
    return of(HEROES);
  }
}

heroes: Hero[] = [];

ngOnInit(): void {
  this.heroService.getHeroes()
    .subscribe(heroes => this.heroes = heroes);
}

服務像資料櫃台：元件只提需求，不管資料現在是寫死的陣列、記憶體模擬還是真正的後端。之後換資料來源，元件一行都不用改。

【Step 7，從伺服器取資料】

HttpClient、刪除與搜尋

🎬 晴光故事

  • angular-in-memory-web-api＝彩排用的假櫃台：沒有真正的後端，也能練完整的流程
  • 搜尋框像請美玲姐查英雄：
    • debounceTime(300)＝美玲姐等你講完（停頓 0.3 秒）才開始查
    • distinctUntilChanged()＝你重複講一樣的名字，她不會重查一次
    • switchMap＝你改問別人，她丟掉舊的查詢只查新的，舊結果不會比新結果晚到還蓋掉它
  • 變數名稱結尾的 $ 像信封上蓋的「掛號」章：提醒你這是 Observable，不是語法

🗺️ 圖解｜Step 7：請美玲姐查英雄的三道關卡

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient()
  ]
};

private heroesUrl = 'api/heroes';

getHeroes(): Observable<Hero[]> {
  return this.http.get<Hero[]>(this.heroesUrl)
    .pipe(catchError(() => of([])));
}

deleteHero(id: number): Observable<unknown> {
  return this.http.delete(`${this.heroesUrl}/${id}`);
}

searchHeroes(term: string): Observable<Hero[]> {
  const value = term.trim();
  return value
    ? this.http.get<Hero[]>(`${this.heroesUrl}/?name=${value}`)
    : of([]);
}

教學用 angular-in-memory-web-api 模擬伺服器：安裝後在 app.config.ts 設定，它會在瀏覽器端攔截 HTTP 請求、回傳假資料，讓你沒有後端也能練完整的增刪改查；正式產品改接真正的 API。這個套件與各 Angular 版本的相容性、standalone 的設定細節，動手前照套件目前的文件確認。

搜尋輸入交給 RxJS 的 Subject<string>（一種可以手動塞值進去的 Observable；Observable 是 RxJS 的資料流物件，值會陸續送來、要訂閱才拿得到），再串三個運算子：debounceTime(300) 等使用者停頓 300 毫秒才動作、distinctUntilChanged() 忽略跟上次相同的字串、switchMap 一有新搜尋就改訂最新的請求，舊請求的結果不會蓋掉新的。

private searchTerms = new Subject<string>();

heroes$ = this.searchTerms.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(term => this.heroService.searchHeroes(term))
);

search(term: string): void {
  this.searchTerms.next(term);
}

searchTerms 是元件內部實作，設 private；heroes$ 要在樣板搭配 async 管道使用，所以保持可存取。名稱結尾的 $ 是「這是 Observable」的命名慣例，不是 TypeScript 語法。
